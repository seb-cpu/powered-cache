Your homepage is fast on the server, but it’s blocking itself in the browser.

Good news first: your server answers in 148 ms and Redis object cache is live — the host isn’t the problem. The 8.0 s largest-paint comes from the page fighting itself: a dead Universal Analytics tag (UA-106137366-1, retired by Google) still ships 62 KB of unused JavaScript, a Google Font blocks the first render, your hero image isn’t preloaded, and WPBakery loads 40 KB of CSS this page never uses. None of this needs a developer — every fix below maps to a switch SwiftPress already has.

4 findings · 3 one-click
01

A dead analytics script is shipping 62 KB of unused JavaScript

−62 KB JS · UA-106137366-1 · 0 executions

Universal Analytics was switched off by Google in 2023, but the tag still loads on every page and blocks the main thread. Turning on js_delay defers it (and GTM) until the visitor interacts — instant LCP relief with zero visual change.

confidence 0.96
02

A Google Font is blocking your first paint

render-blocking · fonts.googleapis.com · ~480 ms

The font request sits in the critical path with no font-display, so text waits on the network. Enabling enable_font_optimization self-hosts it, adds font_display_swap, and preloads the above-the-fold weight — text paints immediately, and it’s GDPR-friendlier too (no call to Google).

confidence 0.94
03

Images without dimensions are shifting your layout

CLS 0.164 · 7 images · missing width/height

Browsers can’t reserve space before images load, so content jumps. add_missing_image_dimensions writes the intrinsic width/height back into the markup — this alone should pull CLS under the 0.1 “good” threshold.

confidence 0.91
04

40 KB of WPBakery CSS is unused on this page

−40 KB CSS · js_composer · +35 KB dashicons

Removing unused CSS is real engineering, not a guess — so SwiftPress does it algorithmically, not with AI. The Remove-Unused-CSS engine isn’t shipped yet; I’ve flagged it rather than offering a switch that does nothing. Coming with the CSS engine.
